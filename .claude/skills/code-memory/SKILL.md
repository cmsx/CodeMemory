# Code Memory Service — скилл

Сервис хранит знания о коде как markdown-заметки в `.memory/` с производным SQLite-индексом. Этот скилл учит **когда** звать инструменты и **как** оформлять capture — не что такое сервис.

## Когда искать — триггеры

- **Начало планирования задачи** — вызови `list_entities` (доменная карта), затем `search` по теме.
- **Пользователь упомянул доменную сущность** — `search` с `anchors: ["entity:Name"]`.
- **Перед правкой файла** — `search` с `anchors: ["file:relative/path"]`.
- **Большой файл** — сначала `list_symbols_in_file`, затем точечный `Read` нужного диапазона символа — не чтение файла целиком.
- **Работа с env-переменной** — `search` с `anchors: ["env:VAR_NAME"]`.

### Порядок при разборе задачи

**сущность** (широкая карта) → **текст** (сужение по симптому) → **файл** → **символ** (точно, перед правкой)

Каждый шаг у́же предыдущего. В текстовом поиске стоит попробовать 1–2 переформулировки.

## Как читать выдачу

- Компактный список `search` — прочитать целиком, выбрать релевантное по `summary`.
- `get_notes` по выбранным `id` — одним вызовом для нескольких заметок.
- Карта якорей развёрнутой заметки — координаты для чтения кода (файл, символ, строки).
- Блок «Упомянутые заметки» (`[[id]]`) — решать по `summary`, дозагружать ли через `get_notes`.
- `stale`-якорь в выдаче — показать пользователю, не игнорировать.

## Когда сохранять — capture

Поводы:

- решение, выкристаллизовавшееся по ходу реализации;
- нетривиальная отладка: что пробовали, почему сработало;
- edge case или хрупкое поведение;
- факт, выясненный практикой, которого нет в документации;
- архитектурное решение;
- исследование незнакомого кода — investigation-заметка.

Не сохранять: переименование, опечатка, тривиальная правка без рассуждения. Пустая заметка засоряет выдачу.

**Процесс:** перед закрытием задачи — сформировать черновик, вызвать `create_note`, показать результат пользователю на review, после подтверждения зафиксировать.

## Шаблоны тела

**Обычная заметка:**

```
## Что сделано
Результат в 2–3 предложениях, не пересказ диффа.

## Ключевые решения и почему
Почему именно так — главная секция.

## Что пробовали и отбросили
Подходы и причины отказа. Не опускать — спасает от повторения ошибок.

## Подводные камни
Gotcha'и, инварианты, cross-effects.

## Ограничения
Незакрытое, осознанные компромиссы.
```

**Заметка-исследование** (разбор незнакомого кода):

```
## Verified
Проверено кодом или подтверждено пользователем.

## Hypothesis
Правдоподобно, но не проверено. Явная, видимая пометка.

## Подводные камни / Ограничения
При наличии.
```

### summary

Авторская строка-анонс: **что заставит будущего агента открыть эту заметку целиком**. Не пересказ slug'а и не первое предложение тела.

### Якоря и веса

Якорь заводится только для предметно затронутого файла/символа. Один предмет обычно якорится на нескольких уровнях: `entity:Name`, `file:path`, `symbol:path#name`.

Вес — две оси:

- **Центральность:** `core` (основная работа), `supporting` (существенно связан), `incidental` (предметно затронут, не главное).
- **Приоритет:** `critical` — заметка содержит инвариант, который обязан увидеть каждый, кто трогает этот якорь. Ставится скупо — только для настоящих констрейнтов. `critical` — это не «очень `core`».

## Рефакторинг

После переименования символа или файла — **обязательно** вызови `rename_anchor` с `old_uri` и `new_uri`, чтобы связи заметок не стали `stale`.

## Незарегистрированная сущность

Если `create_note` отклонён из-за якоря на незнакомую сущность — предложи пользователю `create_entity` с кратким описанием «что это и зачем», после подтверждения повтори `create_note`.

## Происхождение знания

При выдаче заметки со `status: draft` или с секцией `## Hypothesis` — явно пометь это в ответе пользователю: «по непроверенной заметке / по гипотезе — проверьте перед действием».

## Антипаттерны

- Звать `search` на каждый тривиальный шаг — у поиска ограниченные триггеры.
- Разворачивать все результаты `get_notes` вместо выбора по `summary`.
- Создавать заметку без рассуждения (переименование, опечатка).
- Пересказывать в заметке дифф или документацию фреймворка.
- Игнорировать `stale`-якорь в выдаче.
- Помечать `critical` рядовое решение.

## Онбординг существующего проекта

Используется только при подключении сервиса к уже существующему проекту — чтобы дать стартовый seed. Основной режим работы — органический рост через capture в живых сессиях.

Онбординг skill-driven: своих MCP-инструментов и CLI-команд нет. Всё — поверх обычных инструментов (`search`, `get_notes`, `create_note`, `create_entity`, `update_note`).

### 1. Бутстрап структурного индекса

Запусти `cms reindex` — строит `symbol_index` через tree-sitter, чтобы `symbol:`-якоря резолвились. На пустом индексе происходит автоматически.

### 2. Setup

Человек объясняет **логику преобразования**: где лежат источники, как сырьё отображается в заметки (например: «спеки в `docs/`, секция уровня `##` = одна заметка»).

Объявляются **стартовые сущности**: предложи кандидатов из структуры кода, человек прорежает, одобренные регистрируй через `create_entity`.

### 3. Цикл по чанкам

Источник скармливается частями — за один проход всё не усвоить. Для каждого чанка:

1. Прочитай чанк, определи, про какие сущности и файлы он.
2. `search` — есть ли уже относящиеся заметки.
3. Решение: `create_note` с `status: draft` (новое знание), `update_note` (уточнить существующую), или пропуск (уже покрыто).
4. Сбрось сырой текст чанка перед следующим.

**Хранилище как сквозная память:** между чанками сбрасывается сырой текст — чтобы он не подмешивался в интерпретацию следующего документа. Но заметки из ранних чанков остаются доступны через `search` — это дедупликация вместо дублей.

### 4. Review

Draft-заметки просматриваются человеком — пачкой или по ходу — и промотируются в `current` через `update_note`. Непроверенное остаётся `draft`.

### Scratch-файл

Онбординг многосессионный. Между сессиями персистится `.memory/onboarding.md`: план, правила преобразования, чек-лист источников (обработано / в очереди / пропущено). Строительные леса — удаляются по завершении.

### Нечёткие источники

Если у источника нет явного намерения документировать решения (тесты, миграции, общая документация):

- Заметка создаётся только при **проверяемом артефакте-источнике**: символ существует по индексу, тест — артикулированный инвариант.
- «Почему так» без явного источника **не реконструируется** — это интерпретация, LLM заполнит пробел выдумкой.
- При неуверенности — investigation-форма: `Verified` / `Hypothesis`, гипотезы помечены явно.
- Общая концептуальная документация без привязки к коду в заметки не превращается.

### Граница автоматики

В заметку попадает только **артикулированное** — в спеке, в обсуждении, в проверяемом артефакте. Извлечение — это перевод источника, не реконструкция общих представлений.
