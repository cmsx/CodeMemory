# User Stories: Клей между Бизнесом и Системой

В классическом Agile User Stories ("Я как пользователь хочу X, чтобы Y") часто остаются слишком абстрактными и "блеклыми". Для LLM такие истории бесполезны: они не дают понимания, какие именно модули, таблицы и компоненты затрагиваются. 

В нашей архитектуре User Stories — это не просто требования, это **Живая Функциональная Карта**. Это клей, который связывает бизнес-задачу с конкретными системными узлами.

## Концепт "System-Aware Story"

Чтобы история цепляла нужные триггеры, она должна быть двухуровневой:
1.  **Бизнес-уровень (Наблюдаемое поведение):** Что делает актор и что он видит (UI, API-ответ).
2.  **Системный уровень (Под капотом):** Какие внутренние шестеренки крутятся (Очереди, База данных, Интеграции).

Если история затрагивает Ingestion-пайплайн, она обязана явно упомянуть, что создается `IngestionJob`, а не просто "документ обрабатывается". Это заставляет LLM при планировании (в Architect Mode) сразу видеть пересечения слоев.

## Скилл `/storyteller`

Такие истории создаёт скилл `/storyteller`: он берёт уже обсуждённые в
`/grill` требования, маппит каждый бизнес-шаг на конкретные системные узлы
(Specs: доменная модель, фичи) и выдаёт артефакт строгого формата. Режим и
механика — [`../workflow/skills.md`](../workflow/skills.md).

## Идентичность и ссылки

Истории устроены **identity-first** — как заметки Code Memory: идентичность несёт
короткий стабильный ID, а не путь.

*   **Дом — `specs/user-stories/`.** Сквозной верхнеуровневый артефакт, вне слоёв
    `specs/`: история несёт `system_reaction` (техреализацию), поэтому не лежит в
    `product/`. Раскладка внутри дома свободная и реорганизуемая (по фиче,
    механизму, пакетам) — путь не несущий.
*   **ID, не путь.** У истории короткий стабильный глобально-уникальный `id`
    (4–5 символов). Имя файла — `<id>-<slug>.md`, где `<id>` — префикс, а
    `<slug>` — kebab-case от goal только для читабельности и поиска по ФС.
*   **Ссылка по ID, не по пути.** Потребители (`/blueprint`, `/validate`,
    эшелоны планов) ссылаются на историю по `id`; путь и `<slug>` менять можно
    свободно. Резолв ссылки — glob `**/<id>-*.md`.
*   **E2E-тест несёт id истории.** Связь между требованием (история в спеке) и
    верификацией (E2E-тест в коде консьюмера) — общий `id`, не общая папка. Тест
    несёт `id` истории в имени или докблоке.

## Структура System-Aware Story

Каждая история (файл в `specs/user-stories/`, имя `<id>-<slug>.md`) должна включать:

*   **Frontmatter:** `status`, `related_entities` (какие доменные сущности затронуты).
*   **Метаданные:** `id` (короткий стабильный токен, 4–5 симв.), `actor`, `goal`.
*   **Preconditions:** Что должно быть в БД или кэше до старта.
*   **Steps (Шаги):**
    *   `action`: Что делает актор (клик, API-запрос).
    *   `system_reaction`: **(Ключевое отличие)** Что происходит под капотом. *(Пример: "Запись в таблицу X, диспатч Job Y")*.
    *   `expected`: Наблюдаемый результат (UI обновился).
*   **Postconditions:** Финальное состояние системы.
*   **Negative Paths (Альтернативные ветки):** Обработка ошибок, валидация.

*Внедряя `system_reaction`, мы заставляем LLM при чтении истории сразу подгружать в контекст нужные технические слои.*

## Шаблон

Файл в `specs/user-stories/<id>-<slug>.md` (`<id>` — короткий токен-префикс,
`<slug>` — kebab от goal):

```yaml
---
status: stable
related_entities: [EntityA, EntityB]
---
```
```yaml
id: <короткий-токен>
actor: <role>
goal: <одно-два предложения>

precondition:
  - <состояние системы до старта>

steps:
  - action: <наблюдаемое действие, например: Клик на "Запуск">
    system_reaction: <реакция под капотом, например: Создаётся IngestionJob, статус Processing>
    expected: <наблюдаемый результат, например: Показывается лоадер>

postcondition:
  - <финальное состояние БД, очередей, интеграций>

negative_paths:
  - description: <что если пошло не так>
    expected: <реакция системы>
```
