# Воркфлоу `/work`

`/work-*` — семейство скиллов для планирования и пошагового выполнения
нетривиальных задач разработки, в котором **план переживает сессии**. В отличие
от встроенного plan mode (живёт одну сессию), `/work` сохраняет план как файлы
в `plans/`, накапливает журнал решений и отклонений, отслеживает прогресс между
сессиями.

Это инструмент разработки, не часть продукта Code Memory Service. Скиллы
project-local — лежат в `.claude/skills/` этого репозитория.

## Набор команд

| Команда | Назначение |
|---------|------------|
| `/work-prime` | Загрузить контекст проекта (спека + активный план). Режим не запускает. |
| `/work-grill` | Допрос/обсуждение плана или решения. Файлы не пишет. |
| `/work-plan` | Создать новый план из обсуждения. |
| `/work-update [@path]` | Применить итог обсуждения к активному плану. |
| `/work [@path]` | Исполнить текущий этап плана. |
| `/work-step-done` | Закрыть текущий этап. |
| `/work-done` | Закрыть весь план. |

Активируются **только** явным вызовом. Разговор о планировании без команды —
не триггер.

## Linux Way — почему мелкие команды

Планирование собрано из атомарных глаголов: `prime` → `grill` → `plan`/`update`.
Каждая команда — одна явная фаза. `/work-grill` структурно не умеет писать
файлы; запись возможна только под `/work-plan` или `/work-update`. Граница фазы
= граница команды — модель физически не может убежать вперёд и начать
оформление, пока обсуждение не закончено. Контроль перехода между фазами —
у пользователя.

Каждый скилл тонкий и подгружает разделяемое ядро `work/core.md` один раз за
сессию.

## Файлы плана

Лежат в `plans/` в корне проекта. Директория плоская (без подпапок) и в
`.gitignore` — план это личное пространство разработчика. Source of truth —
спецификация в `specs/`, она коммитится; план при необходимости пересобирается
из спеки.

- **Индекс** `<prefix>-00-index.md` — цель, контекст, чек-лист этапов, журнал
  заметок (Decisions / Deviations / Edge cases / Future ideas / Open questions).
- **Step-файлы** `<prefix>-NN-<slug>.md` — цель этапа, Definition of done,
  чек-бокс-подзадачи, рабочие заметки.

`<prefix>` — 3–4 буквы, выбирается автоматически при создании плана. Прогресс
= чек-боксы: первый этап без `[x]` в индексе — текущий.

## Жизненный цикл

```
/work-prime → /work-grill → /work-plan
                  ↓
        ┌──── /work ──── /work-step-done ────┐  (повтор по этапам)
        └────────────────────────────────────┘
                  ↓
             /work-done
```

1. **`/work-prime`** — загрузить контекст. Опционально, обычно в начале сессии.
2. **`/work-grill`** — обсудить задачу. Допрос: дерево решений по зависимостям,
   по одному вопросу, с рекомендованным ответом на каждый.
3. **`/work-plan`** — оформить обсуждённое в план (индекс + все step-файлы).
4. **`/work`** — исполнить текущий этап. На старте — лёгкая сверка плана
   с реальностью, продолжение прерванной работы по неотмеченным подзадачам.
5. **`/work-step-done`** — закрыть этап: суммаризировать рабочие заметки
   в журнал индекса, поставить `[x]`.
6. **`/work-done`** — закрыть план: синхронизировать решения со спекой
   и с памятью, перевести статус в `completed`.

`/work-update` применяется между шагами, когда обсуждение в `/work-grill`
изменило план: добавить этап(ы), занести решение, поправить план.

## Разделяемое ядро

`work/core.md` держит дисциплину, общую для всех команд:

- **Инварианты** — один активный план за раз; плоская `plans/`; прогресс
  чек-боксами; файлы пишутся только по явному сигналу.
- **Гранулярность этапа** — этап = один атомарный осмысленный коммит.
- **Таксономия заметок** — пять секций журнала, каждая со своим назначением.
- **Дисциплины** (см. ниже).
- **Шаблоны** индекса и step-файла.

## Дисциплины

- **Design discipline** — избегать антипаттернов (control-flow sprawl, layer
  mixing, дублирование); использовать механизмы фреймворка, а не ручные
  эквиваленты. Применяется и на проектировании, и на исполнении.
- **Testing discipline** — тесты обязательны и пишутся вместе с функционалом;
  тест против спеки, а не под код; покрытие точек отказа, не только happy path;
  багфикс — сначала воспроизводящий тест. Уровни unit + feature; e2e — отдельный
  план.
- **Architectural thinking** — на планировании держать решения в идиомах
  фреймворка. Imperative layer (на входе) — конвенции проекта как ограничение;
  retrospective layer (перед записью) — архитектурный блок в `/work-plan`
  и `/work-update`.

## Интеграция с памятью

Если проект подключён к Code Memory Service (есть скилл `mem`):

- **Чтение** — `/work-prime` грузит доменную карту (`list_entities`),
  `/work-grill` ищет по теме, `/work` — по `file:`-якорям перед правкой.
- **Запись** — `/work-step-done` фиксирует знание о коде через `/mem`
  (`status: current`), очищенное от плановой метаинформации. `/work-done`
  форкает решения: бизнес-уровень → `specs/`, «как пришли» → заметка памяти.
- Индекс плана может держать `[[id]]`-указатели на заметки; резолвятся лениво
  через `get_notes`, когда содержимое реально нужно.

Разделение: `specs/` — бизнес-уровень и каталог паттернов; память — всё про
код и реализацию.

## Технические детали

- Тексты скиллов на английском (экономия токенов); общение с пользователем
  и все артефакты (планы, заметки, правки спеки) — на русском.
- `work/core.md` читается один раз за сессию; повторно команды его не
  перечитывают.
