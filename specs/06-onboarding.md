# Code Memory Service — онбординг существующего проекта

Greenfield-органический рост — основной режим: память набирается заметками
в живых сессиях работы. Онбординг нужен только при подключении системы к уже
существующему проекту — чтобы дать стартовый seed.

Онбординг — **skill-driven**: не каталог команд, а дисциплина процесса поверх
существующих инструментов (`search`, `get_notes`, `create_note`,
`create_entity`, `update_note`). Своих MCP-инструментов и CLI-команд у онбординга
нет.

## Флоу

### 1. Бутстрап структурного индекса

`reindex` строит `symbol_index` через tree-sitter — чтобы `symbol:`-якоря
создаваемых заметок резолвились. Запускается автоматически на пустом индексе.

### 2. Setup

Человек объясняет системе **логику преобразования** для этого проекта: где лежат
источники, как сырьё отображается в заметки (например: «спеки в `docs/`, секция
уровня `##` = одна заметка»). Объявляются **стартовые сущности** — из структуры
кода и знаний человека: Клод предлагает кандидатов, человек прорежает, одобренные
регистрируются через `create_entity`.

### 3. Цикл по чанкам

Документация скармливается **частями** — за один проход LLM всё не усвоит.
Для каждого чанка:

1. Клод читает чанк, определяет, про какие сущности и файлы он.
2. `search` хранилища — есть ли уже относящиеся заметки.
3. Решение: `create_note` (новое знание), `update_note` (уточнить
   существующую) либо пропуск (уже покрыто).
4. Новые заметки создаются со статусом `draft`.
5. Сырой текст чанка сбрасывается перед следующим.

### 4. Review

Draft-заметки просматриваются человеком — пачкой или по ходу — и промотируются
в `current`. Непроверенное остаётся `draft`.

## Хранилище как сквозная память

Между чанками сбрасывается **сырой текст** — чтобы текст одного документа не
подмешивался в интерпретацию другого. Но **заметки**, созданные из ранних
чанков, остаются в хранилище и доступны через `search`. Хранилище работает как
сквозная рабочая память онбординга — вместо контекстного окна. `search` перед
`create` даёт дедупликацию и слияние вместо дублей.

## Прогресс: scratch-файл

Онбординг многосессионный — за один прогон большой проект не усвоить. Между
сессиями персистится `.memory/onboarding.md`: план, правила преобразования,
чек-лист источников (обработано / в очереди / пропущено). Это строительные
леса — удаляется или архивируется по завершении. Сами заметки и реестр
сущностей персистятся штатно.

## Нечёткие источники

Если у источника нет явного намерения документировать решения (тесты, миграции,
маркированные комментарии, общая документация) — флоу тот же, но с усиленной
дисциплиной:

- Заметка создаётся только при **проверяемом артефакте-источнике**:
  существование символа проверяется по индексу, имя теста — артикулированный
  командой инвариант.
- «Почему так» без явного источника **не реконструируется** — это интерпретация,
  и LLM заполнит пробел правдоподобной выдумкой.
- При неуверенности — investigation-форма тела: `Verified` / `Hypothesis`,
  гипотезы помечаются явно.
- Общая концептуальная документация без привязки к коду в заметки не
  превращается.

Разбор по-настоящему чужого кода лучше идёт органически — через `/memory
capture` с investigation-заметками в живых сессиях реальной работы, а не
батч-прогоном.

## Граница автоматики

Постоянный принцип, не только для онбординга: в заметку попадает только то, что
было **артикулировано** — в спеке, в обсуждении, в проверяемом артефакте. LLM
не дополняет запись своими общими представлениями. Извлечение — это перевод
источника, а не реконструкция «почему так».
