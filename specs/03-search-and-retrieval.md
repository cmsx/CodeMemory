# Code Memory Service — поиск и навигация

## Что возвращает поиск

Поиск даёт две вещи сразу:

1. **Знание** — заметки о том, что и как устроено, почему так решено.
2. **Навигационную карту** — список файлов/символов, куда смотреть, чтобы не
   перечитывать всё подряд.

## Два пути поиска

- **Якорный** — точный, по `file` / `symbol` / `entity` / `env`. Основной путь.
- **Текстовый** — BM25 по `summary` и телу заметки. Вторичный путь.

Якоря в одном вызове объединяются по **OR** (union): заметка квалифицируется,
если совпала хотя бы по одному переданному якорю любого вида. Один вызов
принимает произвольный смешанный набор якорей; AND-семантики по якорям и
отдельного флага для неё нет. `query` и `anchors` — раздельные оси, в одном
вызове не смешиваются.

Запрос может опционально нести **контекст работы** (рабочая сущность и т.п.) —
см. ниже про отсечку.

### Текстовый поиск: стемминг и префикс

Термы запроса стеммятся (русский Snowball) и матчатся как префикс — `стем*`.
Русское словоизменение суффиксально, поэтому `стем*` по несклеенному индексу
ловит все формы; переиндексация не нужна, стеммится только запрос. Извлечение
корней — на стороне поиска: LLM формулирует запрос обычными словами на языке
заметок, подбирать корни вручную не нужно. Нерусские термы (идентификаторы
кода) проходят без стемминга.

Термы соединяются **OR по умолчанию** — любой терм достаточен: широкий невод,
а BM25 ранжирует плотнейшее совпадение наверх. Это режим recall по умолчанию
(Story 04), когда точные слова неизвестны. Флаг `strict: true` переключает на
AND — все термы обязательны; сужает выдачу, когда OR-невод даёт слишком много
шума. Выбор режима — за LLM. Широкий префикс в любом режиме сам гасится низким
IDF в BM25.

`strict` — это **AND по стеммированным термам**, не точная фраза по позициям.
FTS5 не поддерживает префиксные токены внутри фразы (`"стем1* стем2*"` не даёт
совпадений), а весь текстовый путь построен на стемминге+префиксе; точная
фраза по сырым словоформам была бы хрупкой для русского и отброшена.

## Ленивая выдача: две фазы

**Фаза 1 — компактная выдача.** Список из `id` + `summary`. Дёшев настолько, что
LLM читает его целиком и сама выбирает нужное. Якоря и тело не отдаются. Статус
в строку не выводится — в дефолтном поиске все заметки `current`; пометка
статуса добавляется только у не-`current` заметок (видны лишь с
`include_archived`).

**Фаза 2 — разворот (`get_notes`).** По выбранным `id` возвращается:

- тело заметки;
- карта якорей `file`/`symbol`, сгруппированная по весу (`critical`/`core`
  сверху), со stale-статусом — курируемый список «куда смотреть»;
- блок «Упомянутые заметки» — `id` + `summary` для всех `[[id]]` из тела
  (со статусом-пометкой, если упомянутая заметка не `current`).

## Ранжирование

```
score = weight × idf × text_relevance
```

Порядок внутри выдачи **малоценен**: LLM получает список и выбирает сама.
Сортировка косметическая — чтобы сильное было сверху; тайбрейк при равном
score — более свежая `updated`. Возраст заметки в score не входит: устаревание
моделируется статусом, не временем.

## Главная работа — отсечка, а не сортировка

Ценна не сортировка, а **граница списка**: что попало, что нет.

- **Точность** — в списке нет шума. Шум стоит токенов и провоцирует развернуть
  ложную заметку (полное тело — тысячи токенов).
- **Полнота** — нет пропусков. Пропуск *обязательного* (инвариант) закрыт
  структурно через `critical`. Пропуск *остального* — это чаще проблема
  формирования запроса (скилл не дёрнул нужный поиск), а не ранжирования.

## Механизмы отсечки

1. **Вес — фильтр членства.** `incidental` и выше квалифицируют заметку
   в выдачу по якорю. Ниже — файл не якорится вовсе. Порог не подбирается —
   переиспользуется классификация, сделанная автором при capture.
2. **`critical` — pinned.** Заметка гарантированно в выдаче по этому якорю,
   поверх лимита и IDF. Структурная гарантия полноты для инвариантов.
3. **IDF — отсечка слабых совпадений.** Совпадение через вездесущий файл —
   слабое, само по себе в выдачу не квалифицирует; заметка попадёт, если есть
   совпадение сильнее по другому якорю. Считается по `file`/`symbol`,
   не по `entity`.
4. **BM25-пол** — единственный числовой порог: текстовое совпадение ниже пола
   не считается совпадением.
5. **`limit` — предохранитель, не резак.** Переполнение выдачи после отсечки —
   сигнал «запрос слишком широкий», а не повод молча выкинуть лишнее по счёту.
6. **Контекст работы — подтверждающий сигнал, не фильтр.** Заметка, совпавшая
   по нескольким критериям (`file:X` + `entity:Order`), релевантна с высокой
   уверенностью. Совпавшая по одному — остаётся в выдаче, если прошла порог веса
   (инвариант про файл X обязан всплыть, даже если к рабочей сущности отношения
   не имеет). Жёсткий фильтр по контексту убил бы полноту.

## Навигация

- **Карта якорей** при разворачивании заметки — точные координаты файлов
  и символов вместо чтения всего подряд.
- **`[[id]]`-цепочки** — заметка ссылается на прежние решения; LLM решает,
  дозагружать ли, по `summary` упомянутых.
- **Порядок поиска:** сущность (широкая карта) → текст (сужение по
  симптому) → файл → символ (точно, перед правкой). Каждый шаг у́же и дёшев.

## Фильтр статуса

По умолчанию выдача — только `current`. `outdated` доступен по явному
`include_archived` (исторические раскопки). `draft` — вне обычного поиска,
доступен по явному `include_drafts`. Флаги независимы и аддитивны: `outdated`
и `draft` — разные оси, каждый флаг добавляет свой статус к набору.

`include_drafts` нужен прежде всего онбордингу: он создаёт заметки как `draft`
и должен находить их при дедупликации перед `create_note` (см. `06-onboarding.md`).

## Векторный (семантический) поиск

Отложен. На корпусе в десятки-сотни заметок BM25 по авторскому `summary` и телу
адекватен, а вариативность формулировок обеспечивает сама LLM, перебирая
запросы. Схема остаётся совместимой — слой добавляется позже без миграции.
Пересмотр — при большом корпусе и наблюдаемых промахах BM25.
